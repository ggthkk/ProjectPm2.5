## ตั้งค่า

คัดลอก `.env.example` เป็น `.env` แล้วใส่ `API_KEY`, `DISCORD_WEBHOOK_URL`, `MAP` เดิม รองรับตัวแปร `map` เดิมด้วย `MAP` มีรูปแบบ `lat,lon;lat,lon` ห้าม commit `.env`

ไม่ต้องมีโดเมนใหม่ ฐานข้อมูลภายนอก หรือเปิดพอร์ต การตั้งค่าพื้นที่เริ่มต้นเป็นกรุงเทพมหานคร (10), นนทบุรี (12), ปทุมธานี (13) เปลี่ยน `WATER_PROVINCES` และ `ALERT_AREAS` ตามสมาชิกจริง

ตั้ง `DISCORD_GAMES_WEBHOOK_URL`, `DISCORD_NEWS_WEBHOOK_URL`, `DISCORD_ALERTS_WEBHOOK_URL`, `DISCORD_WEATHER_WEBHOOK_URL` เพื่อแยกห้องได้ หากไม่ตั้งจะใช้ webhook หลัก ควบคุมหมวดด้วย `ENABLE_*` และเวลา/เพดานด้วยตัวแปรใน `.env.example` หากต้องการรับแจ้งเฉพาะบุคคล ให้สมาชิกเลือกการแจ้งเตือนห้องใน Discord; รุ่น webhook นี้ไม่มีคำสั่งสมัคร role หรือ slash command

```powershell
go test ./...
go vet ./...
go run . -mode=check
go run . -mode=once -dry-run
go run . -mode=daemon
```

`check` ดึงแหล่งข้อมูลจริงและตรวจ parser ไม่ส่ง Discord และไม่เปลี่ยนประวัติ `once -dry-run` แสดงรายงานตัวอย่างจากข้อมูลจริง `once` ส่งรายงานจริงโดยไม่รอเวลาประจำวัน (ใช้แทน daemon ไม่ควรเปิดพร้อมกัน)

## Portainer

1. เพิ่ม Compose stack จาก Git repository `https://github.com/ggthkk/ProjectPm2.5` และ compose path `compose.yml` โดยเลือก commit/ref ที่ตรวจแล้ว
2. ใส่ environment variables อย่างน้อย `API_KEY`, `DISCORD_WEBHOOK_URL`, `MAP` ใน Portainer ไม่ใส่ secrets ลง compose/Git
3. Deploy: Portainer build ด้วย Dockerfile หลาย stage ซึ่งรัน tests ก่อนสร้าง binary
4. ตรวจ container logs: `bot started`, `poll: ... errors=0` และ health `healthy` จากนั้นตรวจ `Discord delivered` หลังถึงเวลาส่งจริง
5. เมื่อ VPS ทำงานแล้ว ปิด workflow `Air Quality Bot` เดิมใน GitHub ก่อนรอบรายงานถัดไป เพื่อไม่ส่งซ้อนกันสองที่

Container จำกัด 128 MiB / 0.25 CPU ใช้ non-root, read-only filesystem, ไม่เปิดพอร์ต และเก็บประวัติใน named volume `digest-data` ต้องคง volume นี้ไว้ระหว่าง update/restart; อย่าลบ volume หรือ scale มากกว่า 1 replica เพราะประวัติเป็น single-writer

## การยืนยันการส่งและ recovery

บันทึกสถานะ `pending` ลงไฟล์ก่อน POST และขอ receipt จาก Discord (`wait=true`) เมื่อยืนยันสำเร็จจึงบันทึก `sent` และ ID ข้อความ ใช้ atomic rename เพื่อไม่ทิ้งไฟล์ครึ่งหนึ่ง

หากเครือข่ายขาดหรือ Discord 5xx จนไม่ทราบว่าส่งสำเร็จหรือไม่ จะเก็บ pending และไม่ส่งซ้ำอัตโนมัติ (ยอมพลาดข้อความเพื่อหลีกเลี่ยงข้อความซ้ำ) ผู้ดูแลต้องตรวจ Discord ก่อนแก้ pending ใน state โดยหยุด container และสำรองไฟล์ก่อนเสมอ หากไฟล์ state เสีย โปรแกรมหยุดแทนการล้างประวัติ

HTTP 4xx รวมถึง 429 ถือว่าปฏิเสธและลองใหม่รอบตรวจถัดไป ไม่วนยิงทันที ความล้มเหลวของแหล่งหนึ่งไม่ทำให้หมวดอื่นหยุด; เก็บใน log โดยไม่แสดง secret หรือส่ง error รบกวนสมาชิก Healthcheck ยืนยันวงรอบโปรแกรมยังทำงาน ไม่ใช่หลักฐานว่า upstream ทุกแห่งหรือการส่ง Discord สำเร็จ

Rollback: กลับไป commit ก่อนหน้าแล้ว redeploy โดยคง volume เดิมไว้ หากกลับไปใช้ GitHub Actions ให้หยุด stack บน VPS ก่อนเปิด workflow เดิม และนำ workflow จาก Git history มาใช้
